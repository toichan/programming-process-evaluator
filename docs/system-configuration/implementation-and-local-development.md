# 段階2: 実装とローカル開発の詳細手順

この文書は、[開発からデプロイまでの全体手順](./development-and-deployment-flow.md)の段階2を具体化したものです。段階1で作成・確認した仕様・設計資料をどの作業に使うかを明示し、既存の画面遷移プロトタイプを、DB をデータの正本とする Servlet / JSP アプリケーションへ置き換える流れを定めます。

本システムでは画面デザインを新たに外部開発することより、既存画面を活用した内部開発を主とします。ただし、画面遷移プロトタイプは実装仕様そのものではありません。画面上の仮データや JavaScript の擬似動作を、本実装の振る舞いとして引き継がないでください。

実際に作る順番と、各作業の前提・変更対象・確認方法は[実装ロードマップ](./implementation-roadmap.md)を参照してください。本書は参照資料・整合ルール・共通実装方針を説明します。

## 3. 実装開始前の整合ゲート

各機能の状態ルールが画面上の状態・遷移・操作条件の正本です。[実装用状態表](../state-rules/implementation-state-table.md)は分野別ルールへの索引であり、独立した状態定義ではありません。実装契約（状態・DB 値・遷移イベントの対応表）を照合し、対応が未合意の箇所は合意してからコードに着手します。

### 3.1 必ず照合する状態・データの差分

- [状態命名標準](../state-rules/state-naming-standard.md)は `saveStatus`、`learningStatus`、`publicationStatus`、`distributionStatus`、`evaluationStatus` を意味別に分離します。状態ルールの旧状態表と現在の専用状態ルールが食い違う場合は、個別の専用状態ルールと実装契約を確認してください。
- 現行DB定義と照合した確認事項は[実装契約 IC-001〜009](./implementation-contract.md#資料間の要確認事項)を参照します。旧定義を前提とした保存先不足と、現在も判断が必要な遷移・運用条件を分けて扱います。
- 課題編集と生徒個人の状態は `tasks` / `task_participations` に分離されています。提出・評価もそれぞれの履歴と関連する状態の更新条件を確認します。
- 演習、アンケート回答、プロンプト版、生徒のセキュリティ属性には保存先が定義されています。テーブルの存在だけで仕様充足や合意済みと判断せず、状態ルール・制約・参照関係まで照合します。
- クラス図、DB 定義、匿名化要件を照合し、個人識別情報・学校 / クラス情報・研究同意情報をどのテーブルに保持し、AI 送信前にどう匿名化するかを決めます。

上記は既存設計の不整合候補です。カラムや状態値をコード側だけで補ったり、画面ごとに別解釈を作ったりせず、必要な仕様・DB 定義を更新して合意してから実装します。既に確定済みの設計は変更せず、対応関係だけを記録してください。

### 3.2 実装契約に含める項目

少なくとも次の項目を機能スライスごとに整理します。

| 項目 | 決める内容 |
|---|---|
| 画面・導線 | 画面ID、URL、遷移元・遷移先、ロール |
| 表示データ | 取得するテーブル・項目、検索条件、表示用 DTO |
| 操作 | フォーム/API の入力、サーバー側検証、成功・失敗時の結果 |
| 権限 | 生徒自身・所属学校・教師・管理者などの参照・更新範囲 |
| 状態 | 状態名、DB 値、イベント、遷移条件、許可する操作、画面表示 |
| 永続化 | DAO の責務、トランザクション、論理削除、履歴の保持 |
| 例外 | 対象なし、権限なし、入力不正、重複送信、外部 API / DB 障害時の応答 |

## 4. 画面プロトタイプを本実装へ活用するルール

### 引き継ぐもの

- 画面レイアウト、余白、色、CSS、画像、画面項目の配置
- 共通ヘッダー、サイドナビゲーション、画面間リンクの意図
- 共有部品と確認・通知 UI の見せ方。新しい通知は[フィードバックUIガイド](../feedback-guideline.md)に従う
- HTML の画面単位とフォルダ分類。ただし、JSP / Servlet の構成に合わせて配置先は調整する

### 本実装へ持ち込まないもの

- HTML に直接書かれたユーザー、課題、提出、評価、クラス、ログ、アンケート等の仮レコード
- JavaScript 内の固定配列や疑似的な CRUD、送信後に画面だけ書き換えるデモ処理
- 固定のログイン成功、権限判定、評価結果など、サーバー確認なしで成功する動作
- サンプル CSV / フォーマットの例示データを、本番実行時の業務データとして読む仕組み

プロトタイプは画面設計資料として残し、本実装では仮データを JSP の固定値に置き換えるのではなく、Servlet → Control → DAO → MySQL の経路で取得・更新します。初期データが必要な場合は、開発専用の seed として管理し、本番データと混同しないようにします。

画面表示の組み立てだけを理由に JSP から JDBC を呼び出さず、Servlet が認可と Control 呼び出しを行い、JSP には表示用データを渡します。更新操作の可否は UI のボタン無効化だけに頼らず、Control 層でも状態・所有者・ロールを再検証します。

## 5. 推奨する実装順序

機能を「画面単位」ではなく、DB から画面表示・更新まで一貫して動く小さな縦切り（vertical slice）で進めます。各スライスで、関連する機能仕様・画面遷移・クラス図・状態ルール・DB 定義を再確認します。

### 5.1 共通基盤と DB の土台

1. `src/main/java` は `servlet/`、`control/`、`dao/`、`entity/` を基本とし、HTTP 入出力とアプリケーション処理を分離します。
2. `src/main/webapp` に JSP、CSS、JavaScript、画像を整理し、画面遷移プロトタイプから必要な画面資産を移します。
3. ローカル設定を外部化します。DB ホスト・DB 名・ユーザー・パスワードを一元化し、Java と Compose で異なる固定値を持たせません。秘密値が Git に含まれないことを確認します。
4. 現在の `Client` にある固定認証情報、`null` による接続失敗通知、空 catch を解消します。接続・Statement・ResultSet は適切に閉じ、SQL は `PreparedStatement` を使います。
5. Flyway をビルドへ追加し、DB 設計に基づく初期マイグレーションを作成します。スキーマとアプリケーション版の対応を保ちます。
6. 必要なテーブル・状態値の不整合を合意済みの DB 定義に反映してから、空 DB への適用と開発用初期データの投入を確認します。

**参照資料:** 機能仕様書の技術スタック、[DB 設計書](../database-design/README.md)、[テーブル定義](../database-design/table-definitions.md)、クラス図、[状態ルール](../state-rules/README.md)、構成ガイド、`build.gradle`、Compose、`.env.sample`。

### 5.2 認証・権限と共通画面制御

1. 生徒・教師・管理者のログイン、ログアウト、セッション、パスワード変更ルールを機能仕様書に合わせます。
2. 全 Servlet / Control 操作でログイン状態とロールをサーバー側で確認します。
3. データ取得・更新クエリ自体に所有範囲を含め、生徒は自身のデータ、教師は所属範囲のデータのみ扱えるようにします。
4. 研究同意が必要な画面・AI 評価のアクセス制御を同意状態と連動させます。
5. 共通エラー、入力検証、CSRF、出力エスケープ、フィードバック UI を用意します。

**参照資料:** [機能仕様書](../function-specification.md)のアカウント・セキュリティ・匿名化要件、[同意・AI クラス図](../class-diagram/04-ai-consent-log.puml)、[同意・アンケート状態ルール](../state-rules/student/survey-state-rules.md)、[フィードバックUIガイド](../feedback-guideline.md)。

### 5.3 学生の課題学習スライス

この順序で、各段階のデータを DB に保存し、次の画面で同じユーザー権限に基づいて読み戻せることを確認します。

1. 同意状態の表示・回答と、未同意時のアクセス制御
2. ログイン済み生徒向け課題一覧。公開・配信対象・期限等の条件で DB から取得
3. 課題詳細と保存済み下書きの取得
4. エディターの自動保存・手動保存。機能仕様に沿った30秒間隔のコードスナップショット、イベント種別、時刻の記録
5. コード実行要求のサーバー側検証と Python 実行基盤への安全な引き渡し
6. 想定入出力チェック。仕様どおり不一致でも提出操作自体は継続可能にする
7. 提出の確定、提出後編集制御、再提出可否、重複送信対策
8. 提出時の評価要求、評価中・完了・失敗の表示、学生向け評価結果・根拠・コードログの表示
9. 授業演習のファイル・進捗保存。課題モードと分離し、30秒コードログ収集を行わず、ファイルごとの最終保存コードのみを保持
10. アンケート回答と提出済み状態の保存

課題モードの `saveStatus` と提出状態、学習状態、評価状態を混同しません。画面状態の変更は、状態契約に従った DB 更新後に表示へ反映します。サーバー側保存前に成功通知を表示したり、ブラウザー内だけの値を保存済みとして扱ったりしないでください。

**参照資料:** [機能仕様書](../function-specification.md)の学生向け機能、[学習フロー図](../class-diagram/01-core-learning-flow.puml)、[評価図](../class-diagram/02-evaluation-rubric.puml)、[エディター状態ルール](../state-rules/student/editor-state-rules.md)、[評価状態ルール](../state-rules/student/evaluation-state-rules.md)、[演習状態ルール](../state-rules/student/exercise-state-rules.md)、[アンケート状態ルール](../state-rules/student/survey-state-rules.md)、課題・テストケース・ヒントの[フォーマット](../format/)。

### 5.4 教師の課題管理・配信・評価スライス

1. 教師が参照できるアカウント・クラス情報を DB から取得します。
2. 課題の作成・編集・下書き保存・公開・要更新・論理削除・復元を実装します。
3. プロンプトとルーブリックの作成・版管理・適用履歴を実装します。過去版を上書きせず、評価対象には利用した版を固定します。
4. 課題と対象クラスを結びつけ、配信設定・開始・停止・再配信と、全体 / クラス別の配信状態を実装します。
5. 課題進捗、提出コード、コードログ、評価一覧を教師の所属範囲で集計します。
6. 教師による評価確認・再評価・一括再評価と、その履歴・監査情報を保存します。
7. アンケート結果・CSV 出力を DB から生成し、エクスポート権限と対象範囲を確認します。
8. 管理者専用の教師アカウント管理は、機能仕様書の優先度と画面遷移資料上の未実装扱いを確認し、対象範囲を合意してから実装します。

状態遷移は画面の JavaScript にだけ実装せず、Control 層で旧状態・操作権限・遷移条件を検証し、許可された遷移のみ DB に保存します。

**参照資料:** [機能仕様書](../function-specification.md)の教師向け機能、[教師・課題・配信図](../class-diagram/03-teacher-task-distribution.puml)、[教師状態ルール](../state-rules/teacher/)、[実装用状態表](../state-rules/implementation-state-table.md)、[DB 設計書](../database-design/README.md)。

### 5.5 Gemini API 評価・支援機能

1. API 呼び出しを画面 Servlet から分離し、Control と Gemini 接続アダプターに境界を設けます。
2. API 送信直前に、氏名・出席番号・自由記述の個人識別情報を除去または置換します。
3. 必要最小限の課題、ルーブリック、提出、コードログだけを送信し、プロンプト版・ルーブリック版・request ID・根拠ログ ID を保存します。
4. 応答 JSON をスキーマ検証し、失敗時の再試行回数・簡略ペイロード・エラー状態を設計書どおり実装します。
5. API キーを設定から読み込み、ログへ秘密情報や個人情報を記録しません。
6. API の成功、タイムアウト、認証失敗、形式不正、レート制限の挙動を確認します。

**参照資料:** [生成AI API連携設計書](../ai-api-integration-design.md)、機能仕様書の評価・匿名化要件、[AI・同意・ログ図](../class-diagram/04-ai-consent-log.puml)、評価・プロンプト状態ルール。

### 5.6 共通の実装ルール

- DB から取得すべき業務データは、HTML / JSP / JavaScript の固定配列や表示用サンプルで代替しません。
- 入力値を検証し、SQL はパラメーター化します。JSP 出力はエスケープし、外部からの更新要求を CSRF 対策で保護します。
- 画面にボタンを表示しない制御に加え、サーバー側でもロール・対象データの所有者・現在状態・許可操作を検証します。
- 更新が複数テーブルにまたがる場合は、整合性を保つトランザクション境界を Control に設けます。
- エラーはログに記録し、利用者には復旧可能な説明を返します。成功したように見せる代替値、握りつぶし、黙った `null` は使いません。
- 同意、匿名化、論理削除、評価履歴、プロンプト / ルーブリック版管理など、研究データの追跡性に関わる情報を画面都合で省略しません。
- 通知・確認 UI は shared feedback の仕組みを利用し、ページごとに native `alert` / `confirm` を再実装しません。

## 6. ローカル開発ループ

V11の学校ポリシー移行はDBトリガーを追加する。バイナリログ有効のMySQLでは通常のアプリユーザーに加え移行用の権限が必要となる。移行時のみ管理権限のある資格情報を使い、アプリ実行は通常ユーザーへ戻す。アプリへSUPERを付与したり共有DBのグローバル設定を変更しない。資格情報をログへ出さない。既存所属の学校・レベルが混在している場合は移行が明示的に停止するため、バックアップと移行前確認を行う。

ローカル起動の具体的な入口は [AGENTS.md](../../AGENTS.md) と [README.md](../../README.md) に従い、段階2では次のサイクルを繰り返します。

1. 変更対象の機能と関連する仕様・画面・状態・DB資料を確認する。
2. 必要なら、先に機能仕様・状態契約・DB 定義の差分を合意済みの内容へ更新する。
3. 1つのユースケースを縦切りで実装する（DB migration → DAO → Control → Servlet → JSP / JavaScript）。
4. `docker compose up --build -d` で Gretty アプリ・DB を起動する。
5. `.env.sample` を確認して作成したローカル `.env` の値で、Tomcat と DB の接続先が一致することを確認する。
6. 実ブラウザーから操作し、DB に保存された値を再読込・別画面・再ログイン後にも取得できることを確認する。
7. 状態遷移、権限境界、入力不正、DB / API 障害を確認し、未確認事項を記録する。
8. 差分を読み、仮データ・一時的な認証情報・デバッグ出力が残っていないことを確認して、作業単位を完了する。

### Gemini API のローカル疎通準備

- Gemini API を実接続する場合は、[AI API 連携設計書のキー設定手順](../ai-api-integration-design.md#26-gemini-api-キーの設定と疎通確認)に従い、`.env` の `GEMINI_API_KEY` を設定します。`.env` は Git 管理外ですが、キーの値をチャットやコミットへ貼らないでください。
- 起動済みコンテナには環境変数が自動反映されないため、キーを設定・変更した後は `docker compose up -d --force-recreate app` を実行します。確認コマンドはキー値を出力せず、設定済みかだけを表示します。
- 接続確認は合成入力だけで行い、実際の生徒提出や個人情報を含むデータを外部送信する前に、データ取扱いと本番運用条件を確認します。
- ローカル `.env` を本番へ流用せず、本番用シークレットストアから実行時に注入します。

現時点では自動テスト基盤が十分に整っていないため、テスト追加は機能実装の一部として計画します。少なくとも状態遷移と Control / DAO のデータ処理には再現可能なテストを追加し、実行できない確認は「未確認」と明記します。
