# 実装契約: 状態・データ・画面の対応

この文書は、既存の機能仕様・状態ルール・クラス図・DB 設計を、本実装の Servlet / Control / DAO / JSP で一貫して扱うための確認記録です。個別資料の内容を置き換えず、資料間の対応と合意状況を記録します。

## 使い方

- 実装前に、対象機能に関係する行を確認します。
- 確定していない行を実装者が推測で確定してはいけません。影響、選択肢、推奨案を提示し、仕様責任者の確認後に更新します。
- `確定` にした場合は、根拠資料と確認日を記録し、必要に応じて機能仕様・状態ルール・DB 設計書も更新します。
- 新しい状態やカラムをコードだけに追加しません。仕様と DB 設計の合意後にマイグレーションを作成します。
- 機能ごとの作業前計画は[機能別実装計画テンプレート](./feature-plan-template.md)で作成します。ロードマップの詳細は[実装ロードマップ](./implementation-roadmap.md)を参照してください。

### 復元方針の選択結果

| 案 | 復元後の動作 | 影響 |
|---|---|---|
| A: 下書きへ復元（採用） | 内容・関連データを保持して下書きへ戻し、教師が確認して保存・公開を実行する | 状態遷移表の既存記述に沿う。復元だけで期限切れの公開設定や対象クラスへの公開が再開されることを防げる |
| B: 削除前の状態へ復元（不採用） | 削除前が公開中なら公開中へ戻す | 削除前状態を確実に取得する保存契約、期限・対象クラス・プロンプトの再検証、検証失敗時の遷移先が必要 |

A案の合意済み対応（管理者の操作範囲は引き続き要確認）:

- 復元は `archived → draft` とし、`deleted_at / deleted_by_user_id` を解除する。削除と復元の実行者・日時・変更前後は `audit_logs` に保持する。過去の削除履歴を失わないよう業務更新と監査記録を同一トランザクションで扱う。
- 課題内容、クラス別割当、提出・コードログ・評価履歴を復元に伴って削除・初期化しない。復元によるクラス別状態の自動再開は行わない。再公開時に対象クラス・公開日時・期限・プロンプトを再検証する。
- 生徒の新規アクセス・更新可否は課題全体の公開状態とクラス別割当の双方で判定し、割当が公開済みのままでも下書き・論理削除の課題を公開しない。過去の提出・評価は後述の閲覧条件案に従って参照専用で扱う。
- 復元権限は教師の所属範囲・機能権限をサーバー側で検証する。管理者の操作範囲も認可仕様と照合する。
- 「要更新→論理削除」を操作可否表と遷移表の双方に記載する。

### 過去の提出・評価履歴の閲覧条件（2026-10-02・合意済み）

課題の論理削除、旧改訂化、クラス割当のアーカイブは、提出・コードログ・評価履歴を非表示または削除する根拠にはしない。学習記録は参照専用の履歴として保持し、新規着手・コード更新・提出・再提出の可否とは分けて判定する。

| 利用者 | 閲覧条件 | 表示範囲 | 更新可否 |
|---|---|---|---|
| 生徒 | ログイン中の生徒本人と `task_participations.student_user_id` が一致する | 本人の提出全版、各提出に紐づく評価履歴、評価根拠となる本人のコードログ。課題が論理削除・旧改訂・割当終了でも履歴画面から参照できる | 参照のみ。公開中かつ有効な割当等の通常条件を満たさない限り、エディター再開・提出・再提出は不可 |
| 教師 | 対象機能の権限が有効で、対象の `task_class_assignments → classrooms → schools` に対する現在の `teacher_school_permissions.access_status = enabled` を持つ | 許可学校に属する提出全版、評価全版、コードログ。非在籍となった生徒、非アクティブなクラス、旧改訂、論理削除課題も履歴検索では参照できる | 提出・既存評価・コードログは上書き不可。再評価等は新しい履歴行を追加する |
| 管理者 | 通常の教師向け提出・評価画面には入らない | アカウント・権限・監査情報を管理する。学習内容を含む個別記録の閲覧は、別途定義する監査付き運用権限がある場合だけ許可する | 通常業務での内容更新は不可 |

表示と判定は次の規則に統一する。

- 通常の進行中課題一覧から、論理削除課題・旧改訂・アーカイブ済み割当を除外する。提出・評価の履歴一覧には含め、「削除済み課題」「旧改訂」「割当終了」等の参照専用ラベルを表示する。
- 再提出は `submissions.revision_number` を増やした行、再評価は新しい `evaluations` 行として表示する。最新結果を初期表示し、過去版へ切り替えられるようにする。過去行を上書きしない。
- 評価は評価時に使用した `submission_id / rubric_id / prompt_version_id` を固定して表示する。課題の現行改訂や現在適用中のプロンプトへ読み替えない。
- 研究同意状態は研究利用・研究用エクスポートの可否に使用する。本人の学習記録表示と、授業運営に必要な権限内の教師閲覧を同意状態だけで遮断しない。研究利用時の匿名化条件はIC-008で別途確定する。
- 生徒アカウントが停止・論理削除されると本人はログインできないが、保持期間中の履歴は権限内の教師から参照できる。保存期間満了時の匿名化・物理削除はIC-010の管理手順に従う。
- Control では画面から渡された学校・生徒IDを信用せず、提出から課題割当・クラス・学校まで辿って毎回権限を検証する。CSV出力は必ず監査ログへ記録し、画面閲覧ログは既存仕様どおり必要時に記録する。

教師の閲覧権限は、現行DBの `teacher_school_permissions` に合わせて学校単位の現在権限を正本とする。クラスは権限境界ではなく一覧の絞り込み条件として扱い、クラス単位の教師権限テーブルは追加しない。
