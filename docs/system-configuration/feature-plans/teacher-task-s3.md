# 教師課題 S3 初回スライス計画

作成日: 2026-10-05 JST。更新日: 2026-10-06 JST。状態: **実装計画確定。学校単位の課題所属を先行して永続化し、課題の論理削除・下書き復元を実装する。**

## 目的と範囲

- 工程10 S3「公開・改訂・削除/復元」の最初の縦切りとして、課題を論理削除し、削除一覧から下書きへ復元する操作を本実装へ接続する。
- 削除しても課題内容、クラス割当、提出、コードログ、評価、プロンプト版、関連履歴を物理削除・初期化しない。
- 削除後は通常の教師課題一覧と生徒の新規アクセスから除外する。復元後は必ず下書きとし、公開・予約公開を自動再開しない。
- 課題は作成時に有効な学校を必ず1校指定する。課題の `school_id` を正本として保存し、クラス割当は同校内に限定する。
- 削除・復元は作成者に限らず、課題所属校への有効な所属権限と課題管理機能権限を持つ教師に許可する。編集は現行どおり作成者に限定する。管理者操作は含めない。
- 既存課題画面プロトタイプの削除確認、削除済みフィルター、復元確認を本実装へ接続し、デザイン・文言・導線は変更しない。
- 学校単一所属が必須となるため、必要最小限で本実装と画面プロトタイプの学校選択を単一選択・必須にする。その他の画面構成・デザイン・導線は変更しない。
- 初回スライスに含めない: 下書きの公開、予約公開の実行、公開中課題の改訂、学習開始後の複製、期限延長、クラス追加、配信、管理者による課題操作。

## 合意済み契約

1. `draft` / `published` / `requires_update` から論理削除し、`archived` と削除日時・実行者を保存する。
2. `archived` から復元すると `draft` へ遷移する。復元時に公開・予約公開を再開しない。
3. 削除・復元・監査記録を一つのDB transactionで確定し、失敗時は全てrollbackする。監査履歴は復元後も保持する。
4. 課題の子行・提出・評価・コードログは削除しない。クラス割当の削除・初期化もしない。
5. 生徒アクセスの禁止は課題全体の `publication_status` と `deleted_at` を必須条件として維持し、公開済み割当だけで下書き・削除済み課題へアクセスできないことを回帰確認する。
6. 課題更新は作成者境界を維持し、課題の `school_id` 変更を許可しない。新規・更新時に選択校への権限を検証し、指定クラスがすべて同校に属することをサーバー側で確認する。
7. 削除・復元は同校の課題管理権限教師に許可し、操作時点で機能権限と学校所属権限を再検証する。管理者操作は含めない。
8. 同時更新は既存の `tasks.version` を期待値として検出する。重複POSTは既存のrequest token/audit慣例を確認し、二重状態変更や重複監査を避ける。
9. 確認UIは既存の shared feedback を使用する。ユーザーの明示確認なしに削除・復元を確定しない。

## 受入条件

- 削除確認を取消した場合、DB・一覧・監査の業務状態を変更しない。
- 削除成功時に課題は通常一覧から消え、削除済み一覧で復元可能となる。task data、class assignments、participations、submissions、evaluationsおよびaudit historyは保持される。
- 削除済み課題の生徒ホーム表示・editor direct URLは拒否される。復元してもdraft状態なので同様に公開されず、再公開処理も予約公開も開始しない。
- 復元成功後は通常一覧にdraftとして現れ、削除実行履歴はaudit logに残り、復元の実行者/日時も監査できる。
- 他所有者、権限を失った教師、非教師、archivedでない課題への不正操作はサーバー側で拒否される。古いversionでの要求は競合として拒否し、再読込を案内する。
- 課題は学校IDを必ず保持し、学校未選択・複数校・別学校所属クラスの保存をサーバー側で拒否する。保存済み課題の編集では所属校を変更できない。
- 現行デモデータのリセット対象はプロジェクト専用Compose DBだけとする。migrationはデータ削除を行わず、共有DBや他のDBには接続しない。新しい合成デモのログイン情報は固定値にせず実行時に生成する。

### ローカルデモDB再構築手順

1. Composeの `app` だけ停止する。`db` はプロジェクト専用であることを再確認する。
2. `programming_process_evaluator` データベースだけを削除して同名で再作成する。Compose volume全体や他のDBは削除しない。
3. `docker compose run --rm app gradle flywayMigrate` でV1〜V19を適用する。
4. `docker compose run --rm app gradle seedDemoData` を1回実行する。処理はDB名・Compose接続先を確認し、既存ユーザー/学校/課題がある場合は停止する。合成教師 `teacher-demo`、学校・クラス・下書き課題を登録し、パスワードを実行結果へ一度だけ表示する。
5. 認証画面と課題編集画面をブラウザーで確認する。資格情報をコード、DB以外のログ、文書へ保存しない。

V19はmigration時に既存 `tasks` が残っていると変更前に停止する。migrationにDELETE/TRUNCATEは含めない。
- 更新途中の失敗時、課題状態と監査記録の一部だけがcommitされない。
- DB統合・HTTP/browser確認は共有8080/DBではなく使い捨て合成環境で実施する。Gemini実API・実生徒データは不要。
