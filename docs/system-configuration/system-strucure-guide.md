# 新システム構成・フォルダ構成ガイド

新しい Web システムを設計・実装するときに使う、システム全体の構成とファイル配置のガイドです。特定のアプリケーションの機能やデータを定義するものではありません。新システムの要件に合わせ、必要な層・機能・技術を選択してください。

## 1. システム全体構成

```text
利用者のブラウザー
      │ HTTP / HTTPS
      ▼
Web アプリケーション
      ├── Web 層: URL・リクエスト受付、入力検証、認証・認可
      ├── アプリケーション層: ユースケース、処理の調整
      ├── ドメイン層: 業務ルール、データモデル
      ├── データアクセス層: DB 操作、永続化
      └── 画面・静的ファイル: HTML / テンプレート / CSS / JavaScript
                 │
                 ▼
             データベース

開発・実行環境
      ├── ビルドツール: ソースから配布可能な成果物を作成
      └── コンテナ: アプリケーション、DB、補助サービスを分離して実行
```

### 層ごとの責務

| 層 | 責務 | 設計時のポイント |
|---|---|---|
| Web / Presentation | 外部リクエストを受け付け、応答を返す | HTTP の詳細とアプリケーション処理を分離する |
| Application | ユースケースの実行順序やトランザクションを調整する | 画面や DB 製品に依存しない処理を中心にする |
| Domain | 業務上のルール、概念、制約を表現する | プロジェクト固有のモデルとルールを定義する |
| Data access / Infrastructure | DB、外部 API、ファイルなどとの入出力を担う | 接続先や秘密情報を設定として外部化する |
| View / Static resources | 画面表示とスタイル・クライアント側処理を担う | サーバー側処理と表示資産を分けて整理する |

## 2. フォルダ構成の例

以下は、Java Servlet/JSP を使う Web システムを出発点とした構成例です。新システムの規模や採用技術に応じて、ディレクトリ名や層の分け方を調整してください。

```text
.
├── src/
│   └── main/
│       ├── java/
│       │   ├── controller/       # Web リクエストの受付と応答
│       │   ├── service/          # ユースケース・アプリケーション処理
│       │   ├── domain/           # 業務モデル・ルール
│       │   ├── repository/       # データアクセスの抽象・実装
│       │   ├── entity/           # 永続化データやモデルの型
│       │   └── config/           # アプリケーション設定・初期化
│       ├── resources/             # アプリ内リソース・設定テンプレート
│       └── webapp/
│           ├── WEB-INF/           # 直接公開しないサーバー側画面資源
│           └── static/            # CSS、JavaScript、画像など
├── src/test/                      # 自動テスト
├── containers/                    # サービスごとの Dockerfile
├── setup/                         # DB 初期化・開発用セットアップ
├── documents/                     # 要件・設計・運用などの文書
├── build.gradle                   # ビルドと依存ライブラリの定義
├── settings.gradle                # ビルドプロジェクトの設定
├── docker-compose.yml             # ローカル開発用サービス構成
├── .env.sample                    # 必要な環境変数名と記入例
└── .gitignore                     # Git 管理から除外するファイル
```

### ソースコードの分類

| 配置例 | 役割 |
|---|---|
| `controller/` | HTTP リクエストを受け、入力を読み、アプリケーション層を呼び出して画面や応答を返す |
| `service/` | 画面・通信方式から独立したユースケース処理をまとめる |
| `domain/` | システム固有の用語、業務ルール、値の制約を表す |
| `repository/` | データ保存・検索の境界を表し、DB 実装を呼び出す |
| `entity/` | データベースやアプリケーションで扱う構造化データを表す |
| `config/` | アプリ起動時の設定や依存関係の初期化をまとめる |
| `src/test/` | 単体・結合テストなど、ソースの正しさを確認するコードを配置する |

## 3. 実行・開発環境の構成

| 構成要素 | 役割 |
|---|---|
| Web アプリケーションサーバー | HTTP リクエストを受け付け、アプリケーションを実行する |
| データベース | アプリケーションデータを永続化する |
| ビルドツール | 依存関係を解決し、実行・配布用成果物を作成する |
| コンテナ定義 | 実行環境をサービス単位で定義し、開発環境の差を小さくする |
| Compose 定義 | アプリケーション、DB など複数コンテナの起動方法やネットワークをまとめる |

サービス間の接続先、ポート、認証情報は環境設定として管理します。ローカル開発用設定と本番用設定を分離し、秘密情報をソースコードやバージョン管理対象の設定ファイルへ直接記載しない構成にします。

## 4. ルート直下の設定ファイル例

| ファイル | 役割 |
|---|---|
| `build.gradle` | ビルド方式、プラグイン、外部ライブラリ、成果物の作成方法を定義する |
| `settings.gradle` | ビルドプロジェクト名や複数モジュール構成を定義する |
| `docker-compose.yml` | 開発用サービス、ネットワーク、ポート、ボリューム、起動条件を定義する |
| `.env.sample` | 必要な環境変数の名前と記入形式を示す。秘密の実値は含めない |
| `.gitignore` | ビルド成果物、キャッシュ、ローカル秘密情報などを Git から除外する |
| `README.md` | プロジェクトの目的、必要環境、起動・ビルド方法の入口となる文書 |

## 5. コンテナ定義の配置例

```text
containers/
├── app/
│   └── Dockerfile       # アプリケーション実行イメージ
├── db/
│   └── Dockerfile       # 必要な場合の DB 初期設定・拡張
└── build/
    └── Dockerfile       # 必要な場合のビルド専用環境
```

各サービスの Dockerfile は、そのサービスに必要な実行環境と起動方法を定義します。サービスをコンテナ化しない場合や標準イメージだけで足りる場合は、Dockerfile を置かずに Compose からイメージを指定する構成も選べます。

## 6. DB セットアップ資材の配置例

```text
setup/
├── schema.sql           # テーブル・制約などの初期スキーマ
└── seed.sql             # 開発用の初期データ（必要な場合）
```

本番データと開発用データを区別し、初期化スクリプトの適用順序・再実行可否・データ移行方法を設計します。パスワードやトークンなどの実秘密値を初期データに含めないでください。

## 7. 設計文書の配置例

| 配置例 | 目的 |
|---|---|
| `documents/requirements/` | 利用者、要件、受け入れ条件を記録する |
| `documents/architecture/` | システム構成、コンポーネント間の関係、技術選択を記録する |
| `documents/data/` | データモデル、DB スキーマ、データフローを記録する |
| `documents/operations/` | 起動、設定、バックアップ、監視、障害対応を記録する |

文書は実装と一致する内容を保ち、システム固有の機能やデータを一般的な構成ガイドへ混在させないようにします。

## 8. 新システムの設計で決める項目

- Web フレームワーク、実行環境、ビルド方式
- 機能・ドメイン単位のソースコード分割
- DB 製品、データモデル、スキーマ変更の管理方法
- 認証・認可の方式と秘密情報の保管場所
- ローカル、テスト、本番それぞれの設定方法
- アプリケーションと依存サービスの起動・通信方法
- ログ、監視、バックアップ、障害時の復旧方法
- 自動テストの種類と配置

これらはシステム要件に基づいて決める設計項目です。この文書は構成の共通枠組みを示すものであり、個別システムの仕様や技術選定を確定するものではありません。
