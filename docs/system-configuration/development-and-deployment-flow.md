# 開発からデプロイまでの全体手順

この文書は、Programming Process Evaluator を要件確認から実装、ローカル検証、本番環境への公開、運用まで進めるための作業順をまとめたものです。ローカル起動後のクラウド公開を初めて行う場合にも全体像を追えるよう、各段階の目的と完了条件を記載します。

システム固有の機能要件は[機能仕様書](../function-specification.md)、一般的な層・配置の考え方は[システム構成ガイド](./system-strucure-guide.md)を参照してください。この文書は機能仕様や構成ガイドを置き換えるものではありません。

## 1. 前提と現在の状態

### 機能仕様書に記載されている技術方針

| 領域 | 方針 |
|---|---|
| Web アプリケーション | Java Servlet / JSP、Apache Tomcat、Gradle |
| 画面 | HTML / JSP / JavaScript、Bootstrap、CodeMirror |
| アプリケーション構成 | Servlet（HTTP受付・応答）+ Control（アプリケーション処理）+ DAO（データアクセス）、JDBC |
| データベース | MySQL、SQL ベースの Flyway マイグレーション |
| コード実行 | Python 3.x を Docker サンドボックスで実行 |
| AI 評価 | Gemini API を利用する想定 |
| 公開環境 | AWS EC2、Docker / Docker Compose、Nginx + Tomcat |
| HTTPS | TLS を設定し、Let’s Encrypt 等で証明書を管理 |

上記は機能仕様書に記載された方針です。AWS のアカウント、リージョン、ドメイン、具体的な EC2 サイズ、バックアップ保持期間など、デプロイを実施するための設定値は別途決定が必要です。

### リポジトリの現在状態

ローカル開発環境の起動方法は[README](../../README.md)、機能実装の進捗と検証記録は[実装ロードマップ](./implementation-roadmap.md)を参照してください。この文書では状態を重複管理しません。

ルートのComposeは開発用であり、**現状のままインターネットへ公開できる本番構成ではありません**。ローカルで動作することと、本番公開に必要なセキュリティ・運用条件が満たされていることは分けて判断します。未決の本番条件は[本番運用条件の決定記録](./production-operations-decisions.md)に集約します。

## 2. 全体の進め方

```text
要件・設計の確定
    ↓
実装とローカル開発
    ↓
機能・データ・セキュリティ検証
    ↓
本番構成の設計・準備
    ↓
AWS 環境の構築
    ↓
アプリ・DB・ドメイン・HTTPS のデプロイ
    ↓
受け入れ確認・運用開始
    ↓
監視・バックアップ・更新・障害対応
```

| 段階 | 主な作業 | 次へ進む条件 |
|---|---|---|
| 1. 要件・設計 | 機能仕様、画面遷移、DB、構成、未決事項を確認 | 要件と責任範囲が合意されている |
| 2. 実装 | 機能を小さく実装し、コードと DB 変更を管理 | 主要機能の実装が完了している |
| 3. ローカル検証 | ビルド、機能、異常系、データ保存を確認 | 重大な不具合がなく、再現手順がある |
| 4. 公開準備 | 本番構成、秘密情報、TLS、バックアップ、復旧を準備 | 公開前チェックがすべて確認済み |
| 5. AWS デプロイ | EC2 とサービスを構築し、アプリを配置 | 外部公開前の疎通・セキュリティ確認済み |
| 6. 受け入れ・運用 | 実利用相当の確認、監視、更新、復旧訓練 | 運用担当と障害時の手順が明確 |

## 3. 段階 1: 要件・設計を確定する

1. [機能仕様書](../function-specification.md)を読み、対象機能・利用者・権限・入力制約・期待結果を確認します。
2. [画面遷移図](../screen-flow-diagram.md)とプロトタイプを確認し、画面名と導線を仕様に合わせます。
3. [DB 設計書](../database-design/README.md)とテーブル定義を確認します。未決定のデータ項目、論理削除、匿名化、データ保持期間を明確にします。
4. [システム構成ガイド](./system-strucure-guide.md)を参照し、Servlet・Control・DAO の責務と、ビルド・実行・DB接続構成を揃えます。
5. 以下の本番運用上の未決事項について、責任者と決定内容を記録します。
   - AWS アカウント、利用リージョン、予算上限、EC2 の構成
   - 利用するドメイン名と DNS の管理者
   - 本番 DB のバックアップ頻度・保存期間・復旧目標
   - Gemini API キーの管理者、利用上限、障害時の扱い
   - 研究データの保存期間、削除方法、障害時の連絡先
   - デプロイを実施・承認する担当者とメンテナンス時間

**完了条件:** 実装対象と本番運用の前提が関係者間で確認でき、未決事項に担当者が割り当てられていること。

## 4. 段階 2: 実装とローカル開発

段階1で作成・確認した資料を入力として実装します。具体的な作業順と各作業の前提・変更対象・確認方法は[実装ロードマップ](./implementation-roadmap.md)、未合意の状態・DB対応は[実装契約](./implementation-contract.md)、機能単位の計画には[機能別実装計画テンプレート](./feature-plan-template.md)を使います。参照資料・共通実装方針は[段階2: 実装とローカル開発の詳細手順](./implementation-and-local-development.md)を参照してください。

**完了条件:** 他の開発者が手順を再現でき、アプリ・DB の起動、マイグレーション、主要機能の確認方法が記録されていること。画面の仮データや擬似動作が本実装に残らず、画面表示・操作・状態がサーバー側の認可と DB の実データに基づいていること。

## 5. 段階 3: ローカルで検証する

1. Gradle で WAR をビルドし、ビルド結果と依存関係の解決を確認します。
2. DB を初期化した状態と既存データがある状態の両方で、Flyway マイグレーションを確認します。
3. 生徒・教師それぞれのログイン、権限境界、主要画面遷移を確認します。
4. 課題提出、コードログ収集、評価表示、CSV 出力、授業演習の保存分離を確認します。
5. Python サンドボックスの正常系と、タイムアウト・出力上限・資源制限・ネットワーク制限を確認します。
6. Gemini API の正常応答、認証失敗、レート制限、タイムアウト時の挙動を確認します。
7. DB 接続不可、アプリ再起動、入力不正、セッション切れなどの異常系を確認します。
8. 検証したコマンド、結果、未確認事項を記録します。自動テストがない場合は、手動確認の手順を明記します。

**完了条件:** 主要シナリオと重要な異常系の結果が記録され、デプロイを阻む不具合が解消されていること。

## 6. 段階 4: 本番公開の準備

本番は機能仕様書の方針に沿い、まずは単一の AWS EC2 上で Docker Compose を使う構成を想定します。これは設計方針であり、AWS リソースの作成や本番 Compose はまだこの文書だけでは用意されません。

```text
利用者
  │ HTTPS :443 (HTTP :80 は HTTPS へ転送)
  ▼
Nginx (EC2)
  ├── Servlet/JSP アプリケーション (Tomcat コンテナ)
  │      ├── MySQL コンテナ + 永続ストレージ
  │      ├── Python 実行サンドボックス
  │      └── Gemini API (外部 HTTPS 通信)
  └── TLS 証明書 (Let’s Encrypt 等)
```

公開前に以下を整備します。

- **本番用コンテナ定義:** Nginx、Tomcat アプリ、MySQL、Python 実行環境の起動・停止・再起動を定義します。開発用の Gradle watch サービスは本番実行系へ含めず、ビルド済み成果物を配置します。
- **ネットワーク境界:** インターネットには HTTP/HTTPS のみを公開します。MySQL と Tomcat のポートは直接公開せず、SSH は管理者の接続元に限定するか、管理用の安全な接続方式を選びます。
- **秘密情報:** DB の専用アプリケーションユーザー、パスワード、Gemini API キーなどを安全に保管します。リポジトリへ登録せず、EC2 上の設定ファイルを使う場合は閲覧権限を管理者に限定します。
- **データ永続化:** DB データをコンテナの一時領域に置かず、永続ストレージへ保存します。バックアップを別の保存先へ定期取得し、復元テストを行います。
- **TLS と DNS:** ドメインの DNS を EC2 へ向け、Nginx で証明書を設定します。証明書の更新方法と期限切れの検知を確認します。
- **運用保護:** OS とコンテナイメージの更新、ログローテーション、ディスク容量監視、アラート、DB バックアップ、復旧手順を決めます。
- **容量と費用:** 機能仕様書の同時接続数・コードログ容量の前提を使って負荷を見積もり、AWS の最新料金と照らして予算承認を得ます。試算資料は[サーバ維持費・AI API費](../server-cost-estimate.md)を参照し、公開前に前提と価格を再確認します。

**完了条件:** 構成図、公開ポート、秘密情報の配布方法、バックアップ・復旧手順、費用見積もり、運用責任者が確認済みであること。

## 7. 段階 5: AWS 環境を構築してデプロイする

1. AWS アカウントの MFA、管理者権限、予算アラートを設定し、使用リージョンと EC2 のサイズを確定します。
2. VPC とサブネットを準備します。単一 EC2 構成であっても、DB や Tomcat のポートをインターネットへ直接公開しません。
3. セキュリティグループを最小権限で設定します。利用者向けは原則 80/443、管理用 SSH は承認済みの接続元だけに限定します。
4. Ubuntu LTS の EC2 を作成し、OS 更新、管理用接続、時刻同期、ディスク容量を確認します。
5. Docker と Docker Compose を安全な手順で導入し、バージョンと更新方法を記録します。
6. ドメイン DNS を設定し、Nginx と TLS 証明書を構成します。証明書の発行後、HTTP が HTTPS へ転送されることを確認します。
7. DB の永続ストレージとバックアップ先を準備し、アプリケーション用の DB ユーザーと権限を設定します。root アカウントをアプリ接続に使用しません。
8. Git の特定バージョンから WAR と必要なコンテナイメージをビルドします。成果物をどのように EC2 へ渡すか（コンテナレジストリを使うか等）は、チームで決めて記録します。
9. バージョン付きの成果物を EC2 へ配置し、秘密情報を安全に設定して、本番用 Compose でサービスを起動します。
10. Flyway マイグレーションを適用します。既存データがある場合は、バックアップ取得と復元可能性を確認してから実行します。
11. EC2 内部から Nginx、Tomcat、DB、Python 実行環境の疎通を確認し、その後、外部ネットワークから HTTPS 接続を確認します。
12. 受け入れ確認が完了した後に利用者へ URL を案内します。

単一 EC2 構成では、更新時に短時間サービス停止が発生する可能性があります。停止許容時間を決め、利用者への事前告知、切り戻し手順、DB 変更の互換性を確認してから本番反映します。

## 8. 段階 6: 公開後の受け入れ確認と運用

### 公開直後の確認

- HTTPS 証明書が有効で、HTTP から HTTPS へ転送される。
- ログイン、ロール別アクセス制御、主要画面、コード保存・提出、評価、CSV 出力が動作する。
- コード実行がサンドボックス内に限定され、時間・出力・資源の上限が有効である。
- DB のデータが再起動後も保持され、バックアップから復元できる。
- DB や Tomcat のポートが外部から直接接続できない。
- アプリケーションログとエラーログを確認でき、ディスク容量不足やサービス停止を検知できる。
- 匿名化、アクセス範囲、研究データの保存・削除方針が仕様と一致している。

### 継続運用

1. アプリ、OS、コンテナイメージ、依存ライブラリの更新を計画し、更新前に検証環境で確認します。
2. アプリケーションログ、Nginx ログ、DB 容量、ディスク使用率、証明書期限、サービス稼働状態を定期確認します。
3. DB と必要な設定・成果物のバックアップを定期取得し、定期的に復元訓練を行います。
4. 障害時の一次対応、利用者への連絡、復旧判断、データ復元、事後記録の担当者を明確にします。
5. リリースごとに変更点、対象バージョン、マイグレーション、検証結果、切り戻し方法を記録します。

## 10. この文書だけでは確定していないこと

次の項目は、機能仕様書または現在のリポジトリ設定だけでは確定できないため、実際のデプロイ前に決定・実装・検証します。

- AWS アカウント、リージョン、ネットワーク構成、EC2 サイズ、ディスク容量
- ドメイン名、DNS 管理者、TLS 証明書更新方法
- 本番用 Docker Compose、Nginx 設定、Python サンドボックス実装
- コンテナイメージや WAR の保管・配布方法
- DB バックアップの保存先、頻度、保持期間、復旧目標
- AWS と Gemini API の費用上限、アラート、障害時の運用
- 本番データの初期投入・移行・削除手順
- CI/CD の有無と、デプロイの承認・ロールバック方法

これらを決定した後、必要に応じて本書から「AWS 環境構築・デプロイ手順」と「運用・障害対応手順」を独立した文書に分けます。

上記項目の決定・記録は [本番運用条件の決定テンプレート](./production-operations-decisions.md) を使って進めます。機能実装は本番運用条件の確定を待たずに進められますが、段階4・5（本番公開の準備・AWS デプロイ）に入る前に、同テンプレートの各項目を決定済みにしてください。
