# 実装用状態表

## 1. 目的

この文書は、画面本体の状態設計を実装に落とし込むための最小契約である。ここで定義する状態は「画面制御の状態」であり、API や DB の永続モデルは後続の段階で定義する。

> ここでの方針: 1. 画面で何を表示し、どの操作を許可するかを決める 2. その後、データモデルと API の対応表を決める

## 2. 学生向けエディター実装状態表

| 状態 | 表示ラベル | 発火条件 | 編集 | 保存 | 提出 | 次の遷移 |
|---|---|---|---|---|---|---|
| 未提出 | 未提出 | 課題を開いたが、まだ提出していない | 可 | 可 | 可 | 下書き / 提出済み |
| 未保存 | 変更あり | 入力中で保存していない | 可 | 可 | 条件付き可 | 下書き / 未提出 |
| 下書き | 保存済み | 保存したが提出していない | 可 | 可 | 可 | 提出済み / 未提出 |
| 提出済み | 提出済み | 提出を確定した | 不可 | 不可 | 不可 | 評価結果 / 再提出可能 |
| 再提出可能 | 再提出可能 | 提出済み、提出期限内、かつクラス別課題設定が再提出許可 | 条件付き可 | 条件付き可 | 可 | 提出済み / 再提出不可 |
| 再提出不可 | 提出済み | 提出済みで再提出が禁止されている | 不可 | 不可 | 不可 | 既存の確認画面 |
| 進行中 | 進行中 | コード編集または回答が継続中 | 可 | 可 | 条件付き可 | 下書き / 提出済み |

### 2-1. 実装上の注意点

- 「保存状態」と「学習状態」は分離して管理する。
- 「下書き」は提出前の保存済み状態であり、「提出済み」と同一視しない。
- 提出後の編集制限は画面表示とボタン制御で管理し、バックエンドの判定と同じルールに揃える。
- 再提出は期限内かつ `task_class_assignments.resubmission_policy = allow` の場合だけ許可し、過去版を上書きせず `submissions.revision_number` を増やす。
- 期限後の初回提出は `task_class_assignments.late_submission_policy = allow` の場合だけ許可し、受理後の期限後再提出は許可しない。
- 画面遷移時の未保存確認は、状態が未保存または下書きである場合に表示する。

## 4. 実装時の状態ルールまとめ

### 4-1. UI 制御の原則

- 画面上の状態は「表示ラベル」と「ボタン有効化」を制御するための変数として扱う。
- 状態変化はイベントに応じて遷移する。
- 直接上書きは避け、必要に応じて新しい状態へ遷移させる。

### 4-2. 対照表の更新方針

- 表示ラベルは状態名と UI 文言を一致させる。
- ボタンの有効/無効を状態に紐付ける。
- 例外メッセージは状態ごとに固定する。

## 5. この時点でやらないこと

以下はこの段階では扱わない。

- データベースのテーブル設計
- API リクエスト/レスポンスの JSON 仕様
- サービス層のメソッド責務一覧
- 永続化のリポジトリ設計

これらは、画面状態の契約が固定された後に設計する。現在の主目的は、実装前に「何を状態として扱うか」を確定することである。
