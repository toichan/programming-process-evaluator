# アカウント状態ルール（IC-009）

## 対象

利用者向けIDは生徒`student_id`・教師`teacher_id`で統一し、どちらも`users.login_id`を正本とする。生徒の別表示名・旧生徒コードはUIに出さない。認証・履歴関連付けの`user_id`、研究用識別子、ロール境界、パスワード要件は変更しない。

管理者は1アカウント、IDは小文字`admin`固定とする。教師ログインで入力IDが正確に`admin`で、パスワード・利用中状態・管理者ロールの検証に成功した場合だけ管理画面へ遷移する。大文字/小文字違いでの管理者ログインや、一般利用者による予約IDの使用は許可しない。教師本人の任意パスワード変更は[ロードマップ](../../system-configuration/implementation-roadmap.md)工程12aの未実装範囲であり、強制変更は引き続き導入しない。

- ログイン認証
- セキュリティレベルの違いによるパスワード運用
- 初回ログイン・パスワードリセット後の強制変更フロー
- アカウントの停止・論理削除

## 1. 目的

この文書は、認証・アカウント状態における状態定義、遷移条件、ログイン可否、例外処理を定義する。学習記録（提出・評価・コードログ等）の保持方針とは独立して、アカウント自体の状態を管理する。

## 2. 状態語彙

### 2-1. アカウント状態（`accountStatus`）

- 利用中（`active`）
  - 通常にログイン・操作が可能な状態。
- 停止中（`suspended`）
  - 教師・管理者が一時的にログインを禁止した状態。
- 削除済み（`deleted`）
  - 論理削除され、ログインができない状態。学習記録は参照専用で保持する。

### 2-2. セキュリティレベル（`securityLevel`）

- レベル1（`level1`）
  - 教師が設定したパスワードを生徒が継続利用する運用。
  - 生徒側でのパスワード変更機能は提供しない。
  - 強制変更フローは発生しない。
- レベル2（`level2`）
  - 初期パスワードおよびパスワードリセット後のパスワードでの初回ログイン時に、強制変更フローへ遷移する運用。

### 2-3. 初回ログイン状態（`firstLoginStatus`、レベル2のみ有効）

- 未完了（`pending`）
  - 強制変更が必要だが、まだ完了していない状態。
- 完了（`completed`）
  - 強制変更が完了し、通常ログインに戻った状態。

## 3. 状態遷移

| 現在状態 | 遷移先 | 条件 |
|---|---|---|
| 利用中 | 停止中 | 教師・管理者が停止操作を行ったとき |
| 停止中 | 利用中 | 教師・管理者が停止解除を行ったとき |
| 利用中 | 削除済み | 教師・管理者が論理削除を行ったとき |
| 停止中 | 削除済み | 教師・管理者が論理削除を行ったとき |
| 未完了（初回ログイン） | 完了 | レベル2の生徒が強制変更フローでパスワードを変更したとき |

- 削除済みからの復元（再度「利用中」へ戻す操作）は、本文書の対象外とし、必要になった場合は別途運用ルールを定める。

## 4. ログイン可否マトリクス

| アカウント状態 | ログイン可否 | 備考 |
|---|---|---|
| 利用中 | 可 | 通常ログイン |
| 停止中 | 不可 | ログイン試行はログイン履歴に失敗として記録し、理由を「停止中」として区別する |
| 削除済み | 不可 | ログイン試行はログイン履歴に失敗として記録し、理由を「削除済み」として区別する |

## 4-2. ログイン試行制限

- 同一の利用中アカウントでログインに5回連続して失敗した場合、30分間ログインをロックする。
- ロック中の試行は拒否し、ログイン履歴にはロック中であることを内部理由として記録する。画面には資格情報を特定できない共通メッセージを表示する。
- 30分経過後、次のログイン試行時に失敗回数とロック期限をリセットして再試行可能にする。
- 正常ログインおよび教師による解除時も、失敗回数とロック期限をリセットする。教師解除は `audit_logs` に実行者・対象・操作結果を記録する。
- 未知のログインID、停止中・削除済みアカウントは、このアカウント単位の失敗回数に加算しない。

## 5. セキュリティレベルとパスワード運用

生徒画面にはレベル名・番号を表示しない。変更可否で案内し、レベル1は灰色のdisabledボタン、初回変更は「不要」と表示する。認証・変更拒否のサーバー制御は引き続きレベルに基づいて行う。

| セキュリティレベル | 初期パスワード設定者 | 生徒によるパスワード変更 | 初回ログイン時の強制変更 |
|---|---|---|---|
| レベル1 | 教師 | 不可 | なし |
| レベル2 | システム自動発行または教師設定 | 可（強制変更フロー経由） | あり（`firstLoginStatus = pending` の間、強制変更フロー以外の操作を制限） |

- レベル2の初期パスワード、リセット後パスワード、および強制変更で設定する新しいパスワードは、半角の英大文字・英小文字・数字・記号の4種類のうち3種類以上を含み、8文字以上32文字以下とする。これは[機能仕様書](../../function-specification.md)のパスワード要件と一致させる。
- レベル2において、`firstLoginStatus` が `pending` の間は、強制変更フロー以外の画面へは遷移できない。
- パスワードリセットが実行された場合、`firstLoginStatus` を `pending` に戻し、次回ログイン時に再度強制変更フローへ遷移させる。
- 強制変更フローの完了をもって `firstLoginStatus` を `completed` に更新し、解除条件とする。

## 6. 例外処理

### 6-1. 停止中・削除済みアカウントでログインを試行した場合

- ログインを拒否し、理由（停止中／削除済み）をログイン履歴に記録する。
- 画面には、停止中と削除済みを区別せず「ログインできません。担当教師にお問い合わせください。」のような共通メッセージを表示し、具体的な理由は管理画面側でのみ確認可能とする。

### 6-2. 削除済みアカウントに紐づく学習記録の扱い

- 提出・評価・コードログ等の既存データは削除せず、教師・管理者が参照専用で確認できる状態を維持する。
- 一覧画面では、削除済みアカウントの生徒を「削除済み」として区別し、通常の操作対象からは除外する。

### 6-3. レベル2でパスワードリセット後に強制変更を完了しないまま離脱した場合

- 再ログイン時も `firstLoginStatus = pending` が維持されるため、強制変更フローへ再度遷移する。

## 7. 責務分担

### 生徒管理の追加契約（工程12、2026-10-07）

- 学校権限と`account-management`機能権限を要求する。クラス権限は既存の学校単位のアクセスモデルに従い、有効な学校内クラスに限定する。管理者ロールで教師操作を代行しない。
- レベル1の継続用、レベル2の変更前の初期/再設定用パスワードだけを暗号化保存して確認できる。レベル2の本人変更完了時に確認用データを削除する。認証ハッシュ・本人変更後のパスワード・監査履歴を復号対象にしない。
- 生徒の`account_version`は再設定・停止/解除・削除と本人パスワード変更で加算する。ログイン時の版と現在版が違う、または停止/削除なら既存セッションを拒否する。本人変更に成功した現在のセッションだけは更新後の版へ更新する。
- 再設定はレベル2に限り、`password_change_required`・`must_change_password=true`へ戻す。削除済みの更新と復元を拒否し、既存の学習・同意・ログイン・操作履歴を保持する。
- 一括削除は全件の更新版と学校アクセスを検証し、全体成功または全体rollbackとする。

### 教師アカウント管理の追加契約（2026-10-06）

- 管理者だけが教師の作成、学校/機能権限変更、停止/解除、論理削除、パスワード再設定を行う。削除済みは復元しない。
- 教師のパスワード再設定はログイン失敗回数とロック期限も解除する。権限変更・停止/解除・削除では既存のログイン試行制限を維持する。
- 作成/再設定パスワードは発行直後のモーダルでのみ表示/コピーする。閉じた後と再読込後は再表示しない。DBと監査にはハッシュまたは操作情報だけを保持し、平文を残さない。
- 教師には強制パスワード変更状態を導入しない。プロトタイプの「次回変更必須」文言は本実装へ移植しない。
- 更新版を比較して競合を拒否する。停止/削除/再設定/権限変更後は既存教師セッションを失効させ、再ログイン時に最新の権限を読む。
- 課題編集とプロンプト設計の利用権限は別々に設定/検証する。未実装の教師機能は権限が有効でも利用可能にはしない。

### 7-1. Servlet

- ログインリクエストを受け、アカウント状態・セキュリティレベル・初回ログイン状態を検証する。
- 強制変更フロー中は、対象外のリクエストを拒否する。

### 7-2. Control

- アカウント状態・初回ログイン状態の遷移ロジックを担当する。
- ログイン失敗理由の判定と記録を行う。

### 7-3. Repository

- アカウント状態、セキュリティレベル、初回ログイン状態、ログイン履歴を永続化する。

## 8. 実装時の優先順

1. アカウント状態の語彙とログイン可否を固定する
2. セキュリティレベルごとのパスワード運用を定義する
3. 初回ログイン状態の強制変更フローを実装する
4. ログイン失敗理由の記録方法を定める
5. 削除済みアカウントに紐づく学習記録の参照方法を整理する

## 9. 実装に向けた注意点

- アカウント状態と学習記録の保持方針は独立して扱う。削除済みでも学習記録自体は消さない。
- セキュリティレベルの正本は学校（`schools.security_level`）とする。管理者だけが設定でき、教師・生徒の個別上書きは不可。生徒登録時に学校のレベルを適用し、学校の`security_level_locked`を不可逆に有効化する。以後は学校名のみ変更可能で、生徒停止・削除・所属終了でもレベル変更は解禁しない。
- `student_profiles.school_id`で学校を固定し、既存の`security_level`は学校設定と一致する互換用の値として保持する。学校所属のない旧データは従来のレベルを保持するが、新規業務登録では学校を指定する。既存データの移行は学校・レベルが一意な場合だけ行い、学校跨ぎ・レベル混在はエラーにして手動判断を必要とする。生徒の学校間移動は今回の対象外。
- ログイン拒否の理由は内部記録としてのみ区別し、生徒向け画面では詳細理由を出さない。
