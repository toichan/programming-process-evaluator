# 学生向けアンケート状態ルール

## 対象

- アンケート画面
- 同意確認画面
- 回答の保存と提出
- 進捗の表示制御

## 1. 目的

第164版: 未保存回答はホーム・他画面・ログアウト・修正取消の共有確認で保護する。再読込/閉じるはブラウザー標準確認。保存/提出の送信時は離脱確認を重ねず、保存失敗で再表示された入力は未保存として保護する。閲覧のみ・保存済み回答では確認不要。

この文書は、学生向けアンケートと同意確認画面における状態定義、遷移条件、表示差分、例外処理を定義する。進捗状態は送信状態とは分離して扱う。

## 2. 状態語彙

- 未回答
  - アンケートに一つも回答していない状態。
  - 画面を開いた、または未保存の入力があるだけでは回答中へ遷移しない。

- 進行中
  - 明示的な下書き保存が受理され、一部回答がサーバーへ保存されたが、まだ未提出の状態。
  - 保存済みの回答から再開できる。

- 提出済み
  - アンケートの回答が確定した状態。
  - 同じ生徒・survey・evaluationの組み合わせでは確認モードで再表示する。第162版から「回答を修正」で明示的に編集し、再提出できる。修正前の提出内容は履歴として保持する。
  - evaluationが異なる場合は、新しい回答履歴を作成できる。

- 同意済み
  - 同意確認に同意した状態。
  - その後のアクセス権限や遷移が変わる。

- 未同意
  - 同意確認を完了していない状態。
  - 必須アクセス制御対象となる。

- 非対象
  - アンケートや同意確認が現在の対象ではない状態。
  - 一覧やページアクセス自体を制限する。

## 3. 状態遷移

| 現在状態 | 遷移先 | 条件 |
|---|---|---|
| 未回答 | 進行中 | 生徒が明示的に下書き保存し、サーバー保存が成功したとき |
| 進行中 | 提出済み | 必須項目を入力し、提出したとき |
| 未同意 | 同意済み | 同意ボタンを押したとき |
| 同意済み | 撤回済み | 同意画面で「同意しない」を選択し、確認ダイアログで変更を確定したとき |
| 不同意・撤回済み | 同意済み | 同意画面で「同意する」を選択し、確認ダイアログで変更を確定したとき |
| 非対象 | 未回答 | 対象となったとき |

## 4. 表示差分

- 「評価の確認」は、表示中の評価に紐づく提出IDを指定して戻る。アンケートの対象指定に使う評価IDを提出IDとして流用しない。再評価で同じ提出に複数評価がある場合も、既存の提出単位の評価画面契約に従う。

### 4-1. アンケート画面

- 第159版: 評価結果/編集ログのアンケート導線も現在の同意、完了評価、有効な課題別設定を確認する。
  不可時は不足条件を表示し、「準備中」と一律表示しない。同意変更・設定追加を自動的な本人回答とは扱わない。

- 未回答: 空欄を表示し、送信ボタンを無効化または案内表示
- 進行中: 回答途中の強調表示
- 提出済み: 提出済みバッジと確認内容を表示

### 4-2. 同意確認画面

- 未同意: 同意案内と選択ボタンを表示
- 同意済み: 既に同意済みの表示と次画面への遷移へ案内
- 非対象: アクセス不可メッセージを表示

## 5. 操作可否マトリクス

| 状態 | 入力 | 保存 | 提出 | 再編集 | 次画面への遷移 |
|---|---|---|---|---|---|
| 未回答 | 可 | 条件付き可 | 不可 | 不可 | 不可 |
| 進行中 | 可 | 可 | 条件付き可 | 可 | 不可 |
| 提出済み | 修正開始後のみ可 | 修正下書き不可 | 修正開始後のみ可 | 可 | 可 |
| 未同意 | 可 | 不可 | 不可 | 不可 | 不可 |
| 同意済み | 不可 | 不可 | 不可 | 不可 | 可 |
| 非対象 | 不可 | 不可 | 不可 | 不可 | 不可 |

## 6. 例外処理

### 6-1. 必須項目が未入力の場合
- 提出ボタンを無効化し、欠けている項目をハイライトする。
- 進行中と未回答の差異を明確にする。

### 6-2. 同意が未完了のままアンケートへアクセスした場合
- アクセス不可の表示または案内画面へ戻す。
- 画面遷移前に同意状態を確認する。

### 6-3. 既に提出済みのアンケートを再編集した場合
- 同じ生徒・survey・evaluationの組み合わせは確認モードで表示し、明示的な修正操作後のみ再提出できる。再提出まで確定済み回答を維持し、旧回答は日時/同意/設問/選択肢付き履歴として同一トランザクションで保存する。保存時に最新同意・有効設定・所有範囲・回答版を再検証する。
- evaluationが異なる場合は別の回答として扱い、新しい回答履歴を作成する。既存履歴は変更しない。

### 6-4. 保存せずに離脱した場合
- 初回の下書き保存前であれば回答状態は未回答のままとし、未保存入力からの再開は保証しない。
- 一度でも下書き保存が成功した回答は、サーバー保存内容から再開できる。

## 7. 実装時の優先順

1. 未回答・進行中・提出済みを分離する
2. 同意状態と回答状態の関連を明文化する
3. 提出可否条件を固定する
4. アクセス制御条件を決める
5. エラーと案内文を統一する

## 8. 実装に向けた注意点

- アンケート状態と同意状態は別物として扱う。
- 未回答と進行中の境界は、最初の下書き保存がサーバーで成功したかどうかで判定する。
- 画面表示は「進捗」ではなく「回答済みかどうか」で整理する。

## 9. 同意状態とAI実行・研究エクスポートの関係（IC-006）

- 教師のアンケート結果確認（第154版）は参照専用。現在の`survey-results`権限・評価に対応する課題割当の学校権限・最新同意`agreed`を毎回検証し、保存済み回答のみを一覧/詳細/集計/出力する。同意撤回後は過去回答も除外し、回答自体は保持する。下書きの開始日時と提出日時を区別し、GET更新による状態/時刻変更を行わない。研究CSV/記述出力のみ監査を記録する。教師自身のアンケートは対象外。

- 同意状態（未確認・同意済み・不同意・撤回）は、アンケートへのアクセス可否のみを制御し、課題学習・授業演習・提出・AIによるルーブリック評価の利用可否には影響しない。
- AI評価リクエストには、実行時点の同意状態を記録として残すが、同意状態を理由に評価そのものを拒否しない。ソースコード編集ログの自動収集も同意状態に関わらず継続する。
- 研究データとしての集計・分析・外部エクスポートには、実行時の最新同意状態を確認する。同意撤回後は、撤回前のデータも含め今後の研究利用から除外する。不同意・撤回済みから同意へ変更した場合は、変更前のデータ（不同意・撤回期間に保存したデータを含む）も今後の研究利用対象とする。記録時の同意状態は履歴として保持するが、それだけで利用可否を決めない。学習記録そのものは削除しない。既に公表・提供済みの結果やデータの取り扱いは別途運用で定める。
- 同じ生徒・survey・evaluationへの提出済み回答は通常確認モードとし、第162版の明示的な修正再提出を許可する。旧回答を履歴へ保存し、別evaluationの回答も保持する。ホームへの遷移は提出保存成功後のみ行う。
- 同意を撤回した場合、アンケート状態は「非対象」へ切り替え、新規回答・再編集を禁止する。撤回前に提出済みの回答は、研究エクスポート対象からの除外を除き保持する。
- 同意の回答後も共通ヘッダーの「研究同意」から変更できる。変更前に共通確認ダイアログへ変更前後と影響を表示し、キャンセルではDBを更新しない。
- 同意変更は既存行を上書きせず、文書版・変更日時付きで`consent_records`へ追記する。最新`consent_id`を現在状態とし、同意済みからの不同意は`withdrawn`、再同意は`agreed`として記録する。古い画面からの更新は最新記録IDとの不一致で拒否する。同じ状態の送信は履歴を増やさない。
