# 学生向けエディター状態ルール

## 目的

この文書は、学生向けエディター画面における状態定義、表示差分、操作可否、例外処理を定義する。保存状態と学習状態を分離し、提出・再提出・保留状態の判定を明確にする。

## 1. 状態語彙

### 1-1. 基本状態

- 未提出
  - 課題に対して提出を行っていない状態。
  - エディターへは遷移可能。
  - 画面上では「未提出」または「未着手」を表す。

- 下書き
  - コードを保存したが、正式提出までは完了していない状態。
  - 画面上では「保存済み」「編集中」などの表記を用いる。
  - 提出済みとは区別する。

- 提出済み
  - 課題の提出が完了している状態。
  - 課題の再編集可否は画面ごとに制御する。
  - 評価結果画面への導線が可能になる。

- 再提出可能
  - 提出済みで、提出期限内かつクラス別課題設定が再提出許可の状態。
  - 画面上では再提出ボタンを有効化する。

- 再提出不可
  - 提出済みであり、再提出が許可されていない状態。
  - 画面上では編集・提出操作を制限する。

- 進行中
  - フォーム入力やコード編集が継続中である状態。
  - エディターでは編集中の通常状態として使用する。

- 未保存
  - 現在の編集内容が保存されていない状態。
  - 保存状態表示を「未保存」とする。

- 保存済み
  - 現在の編集内容がシステムに保存されている状態。
  - 保存後の状態は「保存済み」または「下書き保存済み」とする。

## 2. 状態と表示差分

### 2-1. エディター画面の基本表示

| 表示項目 | 内容 |
|---|---|
| 課題状況 | 「編集中」「保存済み」「提出済み」「再提出可能」などを表示する |
| 保存状態 | 「未保存」「保存済み」などを表示する |
| 実行状態 | 実行の成否と標準出力・エラーの表示を行う |
| 課題情報 | 課題名、説明、実装機能、入力制限、作成時のルール、想定入出力を表示する |
| コードログ | 自動保存の履歴と手動保存の履歴を表示する |

### 2-2. 状態別の表示ルール

- 編集中
  - 保存状態は「未保存の変更があります」
  - 実行・保存は可能
  - 提出前であれば提出可能

- 下書き保存済み
  - 保存状態は「保存済み」
  - 提出前のため、提出ボタンは表示されるが、提出後の状態へ遷移するまで保留
  - 画面遷移時には未保存の警告を出す

- 提出済み
  - 課題状況を「提出済み」と表示する
  - 既定では編集を制限する
  - 評価結果画面の導線を有効化する

- 再提出可能
  - 再提出ボタンを表示する
  - 提出済みであっても、設定に応じて編集可能または再提出に切り替える

- 再提出不可
  - 編集ボタンや提出ボタンを無効化する
  - 「提出済みのため編集できません」のような案内を表示する

## 3. 操作可否ルール

### 3-1. 保存

- 保存は常時可能
- 保存時にコードログへ履歴を残す
- 保存済み状態でも、次の編集があれば未保存状態に戻る

### 3-2. 実行

- 実行は常時可能
- 実行結果は標準出力とエラーの両方を表示する
- 実行時の出力は提出チェックの参考として扱う

### 3-3. 提出

- 提出前の状態では提出可能
- 期限後の初回提出は、課題の `late_submission_policy = allow` の場合だけ許可する
- `late_submission_policy = deny` の期限後提出は拒否し、提出できない理由を表示する
- 提出済み状態では、提出期限内かつ教師が禁止していない場合だけ再提出を許可する
- 提出期限後の再提出は、期限後提出の設定にかかわらず許可しない
- 以前の提出版が評価中または評価完了でも、再提出条件を満たす場合は新しい提出版を作成できる
- 再提出は既存の提出を上書きせず、新しい版として保存する
- 提出確認時には、想定入出力と実行結果の差分を表示する
- 想定出力との不一致は提出拒否条件にせず、チェック結果を提出版へ紐づけて受理する

### 3-4. 編集

- 提出前: 編集可能
- 提出済みで未再提出: 既定では編集不可
- 再提出可能状態: 再提出用の編集または再提出を選択可能
- 再提出開始時は直前の提出コードを編集用下書きへコピーし、元の提出版は読み取り専用のまま保持する
- 再提出確定時は編集用下書きから新しい提出版を作成する

## 4. 例外ケース

### 4-1. 未保存のまま画面遷移した場合
- 画面遷移前に確認ダイアログを表示する
- 「保存して移動」「保存せずに移動」「キャンセル」の選択肢を提供する

### 4-2. 課題が見つからない場合
- エラー表示またはホームへ戻す
- ユーザーにとって分かりやすい文言で案内する

### 4-3. 提出済み課題を編集しようとした場合
- 編集不可とし、メッセージを表示する
- 再提出が許可されていない場合はそのまま閲覧のみとする

### 4-4. 想定入出力に不一致がある場合
- 提出確認時に差分を表示する
- 不一致があっても提出可能とする
- ただし、結果には「不一致あり」の注意を含める

### 4-5. 必須項目が未入力で提出した場合
- 提出前に確認画面を出す
- 必須項目の未入力の場合は提出ボタンの有効化を制御する

## 4-6. 下書きの復元・同時更新・重複提出（IC-002・IC-003）

- 下書き復元
  - エディター起動時は、常にサーバー側に保存済みの下書き（最後の自動保存または手動保存の内容）を初期値として復元する。
  - ブラウザーのローカル保存のみを正とせず、ブラウザー再読込・別端末からのアクセスでも同じ下書きが復元されることを保証する。

- 同時更新の検知
  - 下書きの更新日時を楽観ロックのキーとして保持する。
  - 保存リクエスト送信時にクライアントが保持する更新日時より、サーバー側の下書きが新しい場合は上書きを行わず、「他の画面で更新されています。最新の内容を読み込み直してください」という案内を表示する。
  - 複数タブ・複数端末からの同時編集は許容するが、後勝ちでの無断上書きは行わない。

- 重複提出の防止
  - 提出確定時にサーバー側で提出版の採番を排他制御し、同一下書きに対する短時間の重複送信があっても二重に提出履歴を作成しない。
  - 重複を検知した場合は「提出処理中です」と案内し、直前の提出結果へ遷移させる。

- 学習状態・進捗状態との対応
  - 下書きの初回保存（自動保存・手動保存のいずれか）で学習状態を「未着手」から「学習中」へ進める。
  - 提出確定で学習状態を「提出済み」へ進め、再提出のための編集を開始すると再び「学習中」へ戻す。
  - 教師の進捗一覧向けの進捗状態は、学習状態に加えて評価状態（評価待ち・評価完了・要対応）を合成して表示する。詳細は [teacher/progress-state-rules.md](../teacher/progress-state-rules.md) を参照する。

## 5. 実装時の優先順

1. 状態の命名と区別を固定する
2. 保存状態と学習状態の表示ルールを整理する
3. 提出済み後の編集制限を決める
4. 例外メッセージと遷移確認を定義する
5. 画面の UI とボタン制御を状態に紐付ける

## 6. 実装に向けた注意点

- 「保存済み」は提出済みと同一ではない
- 「編集中」は保存状態ではなく、作業状態である
- 提出済み後の再提出可否は、提出期限と `task_class_assignments.resubmission_policy` の両方で制御する
- 再提出方針は生徒単位ではなく、課題のクラス別割当単位で共通適用する
- 状態変更の責務は、画面表示と API ロジックの両方で明確にする
