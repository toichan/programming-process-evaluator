# 課題状態ルール

## 対象

- 課題編集機能
- 課題一覧の状態表示
- 課題の作成・編集・公開・論理削除・復元

## 1. 目的

この文書は、教師向け課題編集機能における状態定義、遷移条件、表示差分、例外処理を定義する。特に、保存状態と課題の公開状態を分離し、画面上の表示とデータ保存時の責務を一致させる。

## 2. 状態語彙

### 2-1. 基本状態

- 下書き
  - 課題が作成済みだが、公開前である状態。論理削除から復元した課題も含む。
  - 一覧では「下書き」と表示する。
  - 変更や編集が可能。

- 公開中
  - 課題が生徒に公開され、利用可能な状態。
  - 一覧では「公開中」と表示する。
  - 既存の公開中の課題は、内容更新時に「要更新」へ切り替わることがある。

- 要更新
  - 課題内容、ルール、配信条件、プロンプト設定のいずれかに更新が必要になった状態。
  - 一覧では「要更新」と表示する。
  - 一定条件で再公開または差し戻しを行う。

- 論理削除
  - 課題を一覧から非表示にしつつ、データは残す状態。
  - 「削除」ではなく「非表示化」として扱う。
  - 生徒向けには表示されない。

- 期限切れ
  - クラス別課題割当の提出期限を過ぎた状態。課題全体の `publication_status` ではなく、`task_class_assignments.assignment_status` に設定する。
  - 提出期限がある割当に限り、アプリ内定期処理が期限到来後に「公開中」から遷移させる。処理間隔は1分で、期限到来から最大約1分以内に反映する。
  - 期限切れは初回提出の可否を単独では決めない。期限後提出が許可されていれば未提出者の初回提出のみ受け付け、禁止されていれば拒否する。期限後の再提出は許可しない。

### 2-2. 区別すべき概念

- 保存状態
  - フォームの入力内容が保存されているかどうか。
  - 例: 下書き保存済み、未保存

- 公開状態
  - 課題が生徒に公開されているかどうか。
  - 例: 公開中、下書き、要更新、論理削除
  - 課題全体の状態とクラス別割当の状態は分けて管理する。課題全体が公開状態でも、公開予定時刻前の割当は予約中となる。

- これらは同一ではない。
  - 下書き保存済みでも公開中ではない。
  - 公開中でもすべての編集が可能ではない。

## 3. 状態遷移

| 現在状態 | 遷移先 | 条件 |
|---|---|---|
| 下書き | 下書き | 下書き保存を実行したとき（公開・予約公開は開始しない） |
| 下書き | 公開中 | 保存・公開を実行し、公開条件を満たしたとき。クラス別の公開日時は別途判定する |
| 下書き | 要更新 | 既存の課題情報と整合しないとき |
| 公開中 | 要更新 | 課題内容の変更、配信条件の変更、プロンプト変更など |
| 公開中 | 論理削除 | 管理者または教師が削除操作を実行したとき |
| 要更新 | 公開中 | 再編集後に公開を再実行したとき |
| 要更新 | 下書き | 変更が確定していない場合に差し戻したとき |
| 論理削除 | 下書き | 権限を持つ教師が復元操作を行ったとき。公開・予約公開は再開しない |
| 要更新 | 論理削除 | 削除操作を実行したとき |
| 下書き | 論理削除 | 削除操作を行ったとき |

クラス別割当の公開状態は課題全体の状態と独立して遷移する。DB値は「未公開」=`not_published`、「予約中」=`scheduled`、「公開中」=`published`、「要更新」=`requires_update`、「期限切れ」=`expired`、「論理削除」=`archived` とする。

| 現在状態 | 遷移先 | 条件 |
|---|---|---|
| 未公開 | 予約中 | 「保存・公開」を実行し、公開予定日時が将来であるとき |
| 未公開 | 公開中 | 「保存・公開」を実行し、即時公開が指定されたとき |
| 予約中 | 公開中 | 公開予定日時に到達し、アプリ内定期処理が実行されたとき |
| 公開中 | 期限切れ | 提出期限に到達し、アプリ内定期処理が実行されたとき |

定期処理は1分間隔で実行し、時刻判定はDB時刻を基準とする。予約公開は予定時刻から最大約1分以内、期限切れは提出期限から最大約1分以内に反映する。処理は冪等とし、課題が論理削除・下書き・旧改訂になった割当を公開状態へ遷移させない。アプリ停止中に到来した予定は再起動後に条件を再確認し、公開可能なものだけを反映する。

期限切れの割当は、期限後提出方針に応じて提出操作を判定する。`allow` は未提出者の初回提出だけを許可し、`deny` は期限後の提出を拒否する。期限後の再提出はどちらの方針でも拒否する。割当状態の遷移によって既存の提出・評価履歴を変更しない。

## 4. 表示差分

### 4-1. 一覧画面

- 下書き: 「下書き」バッジを表示
- 公開中: 「公開中」バッジを表示
- 要更新: 「要更新」バッジを表示
- 論理削除: 一覧から非表示または別タブに回す

### 4-2. 課題編集フォーム

- 下書き: 「下書き保存」と「保存・公開」を区別して表示
- 公開中: 「編集を終了」「要更新へ戻す」などの状態変更の導線を表示
- 要更新: 再編集と再公開の導線を表示
- 論理削除: 編集フォームにアクセスできないか、復元確認を行う

## 5. 操作可否マトリクス

| 状態 | 編集 | 保存 | 公開 | 再公開 | 論理削除 | 復元 |
|---|---|---|---|---|---|---|
| 下書き | 可 | 可 | 可 | 不可 | 可 | 不可 |
| 公開中 | 条件付き可 | 可 | 不可 | 不可 | 可 | 不可 |
| 要更新 | 可 | 可 | 可 | 可 | 可 | 不可 |
| 論理削除 | 不可 | 不可 | 不可 | 不可 | 不可 | 可 |

### 補足

- 公開中の課題で、対象クラスの全生徒が未着手の場合、編集内容を同じ課題系列の新しい改訂として保存し、再公開までは直前の公開改訂を生徒に表示する。
- 改訂案の作成時は旧課題・旧assignmentを変更せず、新課題を `requires_update`、新assignmentを `not_published` として保存する。改訂案には旧版のprompt適用版を引き継がず、新版のprompt設定を公開前に必須とする。
- 再公開が成功したときだけ、新revisionを `published`、直前の課題を `requires_update` とし、旧assignmentを `archived` にして新assignmentを公開/予約状態へ移す。全変更と監査記録は同じトランザクションで確定し、提出・評価・コードログ履歴は保持する。
- 学習開始判定では課題の非アーカイブassignmentに紐づく参加状態を確認する。エディターを開いただけで作成された `not_started` 参加行は学習開始済みとみなさない。
- 一人でも学習開始済みの場合、学習条件・提出・評価に影響する項目は直接上書きせず、新しい課題として複製する。
- 学習開始後の期限延長と対象クラス追加は、既存の学習条件を不利に変更しない場合に限り許可する。期限短縮、既存対象クラスの除外、公開開始日時の後退は許可しない。
- 提出期限内の再提出は全対象生徒に許可し、教師向けのクラス別再提出設定は設けない。既存の提出・評価履歴は変更しない。
- `論理削除` は実データ消去ではなく、表示制御の一種として扱う。
- 課題は作成時に必ず単一の学校へ所属させる。クラス割当は課題所属校内に限り、学校未選択や別学校のクラスをControlでも拒否する。
- 下書きの編集は作成者に限る。論理削除・復元は、課題所属校への有効な所属権限と課題管理機能権限を持つ教師が行える。操作時に両権限を再検証し、管理者操作は別途合意するまで提供しない。
- 学校所属は課題本体に保持し、クラス割当の有無から推定しない。論理削除・復元でも所属校は変更しない。

## 6. 例外処理

### 6-1. 公開中の課題を編集しようとした場合
- 対象クラスの全生徒が未着手の場合は編集を許可し、同じ課題系列の新しい改訂を `要更新` として保存する。再公開が完了するまで直前の公開改訂を維持する。
- 一人でも学習開始済みの場合、課題説明、実装機能、入力制約、初期コード、テストケース、ヒント、対象クラス、ルーブリックを直接上書きしない。課題内容の変更が必要な場合は新しい課題として複製する。評価用プロンプトは、[プロンプト状態ルール](./prompt-state-rules.md)に従い、新しい版への切替と全体再評価を明示確認した場合に限り例外として許可する。
- 生徒の学習条件・評価へ影響しない教師向け内部情報だけは更新可能とし、監査ログに変更前後・実行者・実行日時を記録する。
- 提出期限の延長と対象クラス追加は例外的に許可する。期限短縮、既存対象クラスの除外、公開開始日時の後退は拒否する。
- 再提出可否を切り替える教師向けクラス別設定は設けない。
- 評価処理中または評価済みの提出がある場合、既存評価行に固定済みの課題内容・ルーブリック版・プロンプト版は不変とする。全体再評価では旧評価を上書きせず、新しい評価行に新プロンプト版を固定して追加する。
- Control は学習開始状態と更新対象項目を再検証し、画面表示だけで編集制限を実現しない。

### 6-2. 配信中の課題に対して編集した場合
- 配信済みクラスに学習開始済みの生徒がいなければ新しい改訂を `要更新` として編集し、再公開まで直前の公開改訂を維持する。
- 学習開始済みの生徒がいる場合は、6-1の変更制限を適用する。
- クラスごとの学習開始状態を確認し、あるクラスの追加や期限延長が他クラスの公開条件を変更しないようにする。

### 6-3. 論理削除した課題を再利用した場合
- 一覧には表示されないため、検索条件やフィルターで除外する。
- 復元先は削除前の公開状態にかかわらず下書きとする。内容・関連履歴は保持するが、公開状態は復帰させない。
- 復元だけではクラス別公開・予約公開を再開しない。教師が対象クラス・公開日時・期限・プロンプトを確認し、改めて保存・公開を実行する。
- 削除マーカーを解除しても過去の削除履歴は保持し、復元の実行者・日時も記録する。DBとの対応は[実装契約](../../system-configuration/implementation-contract.md)のIC-001を参照する。
- 生徒への課題公開は課題全体とクラス別割当の両方を確認する。割当が公開済みでも、下書きへ復元された課題を公開しない。

### 6-4. 公開に必要なプロンプトが未設定の場合
- 課題の保存は可能でも公開は不可とする。
- エラーメッセージは「プロンプト設計が未設定のため公開できません」とする。

### 6-5. 必須項目が未入力の場合
- 保存可能な場合と公開不可な場合を分ける。
- 最低限の必須項目が満たされないときは、公開ボタンを無効化する。

### 6-6. 論理削除・旧改訂・割当終了後の学習履歴
- 課題状態や割当状態を理由に、既存の提出・コードログ・評価履歴を削除しない。
- 生徒本人は本人の履歴を参照できるが、無効な割当から編集・提出・再提出を開始できない。
- 教師は対象機能の権限に加え、対象課題の割当先学校に対する現在の学校権限を持つ場合に履歴を参照できる。クラスは権限境界ではなく絞り込み条件として扱う。
- 通常の進行中一覧では対象外とし、履歴一覧では「削除済み課題」「旧改訂」「割当終了」等の参照専用ラベルを表示する。
- 提出版と評価版の関連を保持し、評価時の課題・ルーブリック・プロンプトの版を現在版へ読み替えない。

## 7. prompt / distribution との関連ルール

### 7-1. prompt設計との関係

- 課題の公開には prompt の設計・設定が必要な場合がある。
- prompt が未設定の場合、公開状態は `要更新` または `下書き` のままとする。
- 未適用の prompt 下書き編集は課題状態に影響しない。
- 公開中課題へ適用する prompt 版の切替は評価条件の変更として扱う。全生徒が未着手なら課題を `要更新` とし、学習開始後でも、[プロンプト状態ルール](./prompt-state-rules.md)に従って対象生徒・評価差分を確認し、全体再評価を明示確定した場合に限り同一課題へ適用できる。プロンプト以外の学習条件を変更する場合は新しい課題として複製する。
- 評価時には実際に使用した prompt 版を固定し、後から上書きしない。

### 7-2. distributionとの関係

- 配信対象のクラスがある場合、課題の公開状態と配信状態は同時に管理する。
- 配信中の課題は編集制限を設ける。
- 配信予定が存在する場合、課題の状態を `公開中` として扱っても、配信有効化前のクラスは別状態を持つ。

## 8. 責務分担

### 8-1. Servlet

- リクエストの受信と入力値の検証を担当する。
- 状態遷移リクエストの妥当性を確認する。
- エラー時はユーザー向けメッセージを返す。

### 8-2. Control

- 状態遷移ロジックを担当する。
- 公開・要更新・削除・復元のルールを実装する。
- 状態変更前後の整合性チェックを行う。

### 8-3. Repository

- 課題の状態値と公開情報を永続化する。
- 論理削除の記録を保持する。
- 履歴情報を保存し、状態の変遷が追跡可能になるようにする。

## 9. 実装時の優先順

1. 状態名を固定する
2. 一覧表示に使う状態バッジを決める
3. 公開中の編集制限を決める
4. 要更新への切り替え条件を定義する
5. 論理削除と復元を行う
6. prompt / distribution 連携を確認する

## 10. 実装に向けた注意点

- `保存状態` と `公開状態` は別物として扱う。
- 公開中の課題は、編集が常に許可されるわけではない。
- 要更新は「更新が必要」であり、「削除」ではない。
- 一覧とフォームでの表示差分を一致させる。
