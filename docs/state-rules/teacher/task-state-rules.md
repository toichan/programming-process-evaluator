# 課題状態ルール

## 対象

- 課題編集機能
- 課題一覧の状態表示
- 課題の作成・編集・公開・論理削除

## 1. 目的

この文書は、教師向け課題編集機能における状態定義、遷移条件、表示差分、例外処理を定義する。特に、保存状態と課題の公開状態を分離し、画面上の表示とデータ保存時の責務を一致させる。

## 2. 状態語彙

### 2-1. 基本状態

- 下書き
  - 課題が作成済みだが、公開前である状態。
  - 一覧では「下書き」と表示する。
  - 変更や編集が可能。

- 公開中
  - 課題が生徒に公開され、利用可能な状態。
  - 一覧では「公開中」と表示する。
  - 既存の公開中の課題は、内容更新時に「要更新」へ切り替わることがある。

- 要更新
  - 課題内容、ルール、配信条件、プロンプト設定のいずれかに更新が必要になった状態。
  - 一覧では「要更新」と表示する。
  - 一定条件で再公開または差し戻しを行う。

- 論理削除
  - 課題を一覧から非表示にしつつ、データは残す状態。
  - 「削除」ではなく「非表示化」として扱う。
  - 生徒向けには表示されない。

- 期限切れ
  - 提出期限を過ぎた状態。
  - 期間の設定が存在する場合にのみ使用する。

### 2-2. 区別すべき概念

- 保存状態
  - フォームの入力内容が保存されているかどうか。
  - 例: 下書き保存済み、未保存

- 公開状態
  - 課題が生徒に公開されているかどうか。
  - 例: 公開中、下書き、要更新、論理削除

- これらは同一ではない。
  - 下書き保存済みでも公開中ではない。
  - 公開中でもすべての編集が可能ではない。

## 3. 状態遷移

| 現在状態 | 遷移先 | 条件 |
|---|---|---|
| 下書き | 公開中 | 保存・公開を実行したとき |
| 下書き | 要更新 | 既存の課題情報と整合しないとき |
| 公開中 | 要更新 | 課題内容の変更、配信条件の変更、プロンプト変更など |
| 公開中 | 論理削除 | 管理者または教師が削除操作を実行したとき |
| 要更新 | 公開中 | 再編集後に公開を再実行したとき |
| 要更新 | 下書き | 変更が確定していない場合に差し戻したとき |
| 論理削除 | 下書き | 復元操作を行ったとき |
| 下書き | 論理削除 | 削除操作を行ったとき |

## 4. 表示差分

### 4-1. 一覧画面

- 下書き: 「下書き」バッジを表示
- 公開中: 「公開中」バッジを表示
- 要更新: 「要更新」バッジを表示
- 論理削除: 一覧から非表示または別タブに回す

### 4-2. 課題編集フォーム

- 下書き: 保存ボタンと公開ボタンを表示
- 公開中: 「編集を終了」「要更新へ戻す」などの状態変更の導線を表示
- 要更新: 再編集と再公開の導線を表示
- 論理削除: 編集フォームにアクセスできないか、復元確認を行う

## 5. 操作可否マトリクス

| 状態 | 編集 | 保存 | 公開 | 再公開 | 論理削除 | 復元 |
|---|---|---|---|---|---|---|
| 下書き | 可 | 可 | 可 | 不可 | 可 | 不可 |
| 公開中 | 条件付き可 | 可 | 不可 | 不可 | 可 | 不可 |
| 要更新 | 可 | 可 | 可 | 可 | 可 | 不可 |
| 論理削除 | 不可 | 不可 | 不可 | 不可 | 不可 | 可 |

### 補足

- 公開中の課題は、内容を編集しただけでは即座に公開状態が解除されるわけではない。
- ただし、重大な変更や配信条件の変更は「要更新」へ切り替える。
- `論理削除` は実データ消去ではなく、表示制御の一種として扱う。

## 6. 例外処理

### 6-1. 公開中の課題を編集しようとした場合
- 編集可能とする場合と、要更新へ切り替える場合を分ける。
- 基本方針: 変更が公開状態に影響する場合は要更新へ切り替える。

### 6-2. 配信中の課題に対して編集した場合
- 配信済みクラスが存在する場合は、編集を制限または要更新へ切り替える。
- 即座の編集反映は行わず、再公開を前提とする。

### 6-3. 論理削除した課題を再利用した場合
- 一覧には表示されないため、検索条件やフィルターで除外する。
- 復元時には元の状態を保持する。

### 6-4. 公開に必要なプロンプトが未設定の場合
- 課題の保存は可能でも公開は不可とする。
- エラーメッセージは「プロンプト設計が未設定のため公開できません」とする。

### 6-5. 必須項目が未入力の場合
- 保存可能な場合と公開不可な場合を分ける。
- 最低限の必須項目が満たされないときは、公開ボタンを無効化する。

## 7. prompt / distribution との関連ルール

### 7-1. prompt設計との関係

- 課題の公開には prompt の設計・設定が必要な場合がある。
- prompt が未設定の場合、公開状態は `要更新` または `下書き` のままとする。
- prompt の更新自体は課題の状態に影響しないが、公開判定時に参照する。

### 7-2. distributionとの関係

- 配信対象のクラスがある場合、課題の公開状態と配信状態は同時に管理する。
- 配信中の課題は編集制限を設ける。
- 配信予定が存在する場合、課題の状態を `公開中` として扱っても、配信有効化前のクラスは別状態を持つ。

## 8. 責務分担

### 8-1. Servlet

- リクエストの受信と入力値の検証を担当する。
- 状態遷移リクエストの妥当性を確認する。
- エラー時はユーザー向けメッセージを返す。

### 8-2. Service

- 状態遷移ロジックを担当する。
- 公開・要更新・削除・復元のルールを実装する。
- 状態変更前後の整合性チェックを行う。

### 8-3. Repository

- 課題の状態値と公開情報を永続化する。
- 論理削除の記録を保持する。
- 履歴情報を保存し、状態の変遷が追跡可能になるようにする。

## 9. 実装時の優先順

1. 状態名を固定する
2. 一覧表示に使う状態バッジを決める
3. 公開中の編集制限を決める
4. 要更新への切り替え条件を定義する
5. 論理削除と復元を行う
6. prompt / distribution 連携を確認する

## 10. 実装に向けた注意点

- `保存状態` と `公開状態` は別物として扱う。
- 公開中の課題は、編集が常に許可されるわけではない。
- 要更新は「更新が必要」であり、「削除」ではない。
- 一覧とフォームでの表示差分を一致させる。
